## 1. 一句话目标

在一个 SoC 项目里,为**每个 chip IP**在**每个角色**下各拉起一个常驻 agent;
同一个 IP 的各角色 agent 之间可以按流程接力通信(如"UART 验证完成 → 通知 UART 软件 agent 开工"),**不同 IP 之间不允许通信**。

## 2. 结构映射(herdr 概念 ↔ 你的业务概念)

| herdr 概念 | 你的业务概念 | 数量 |
| --- | --- | --- |
| workspace | 项目 A 根目录(整个 SoC 项目) | 1 |
| tab | 角色分组("文件夹"),即一类智能体 | 5 |
| pane | 一个 agent,**固定负责一个 IP** | 每个 tab 下 N 个(N = IP 数,例如 30) |

5 个 tab(来自 drawio):

1. Spec 智能体
2. 架构智能体
3. RTL 智能体
4. 验证智能体
5. 软件智能体

每个 tab 下的 agent 都是基于 **pi 二次开发**的,代码基底相同,只是职能不同(drawio 里每个 tab 下都画了 IP 1 … IP n)。

规模估算:30 个 IP × 5 个角色 = **150 个 agent/pane**。(drawio 只画了 IP 1 到 IP n,实际是否 5 个 tab 都覆盖全部 IP,请确认,见 §6 Q1。)

## 3. 各角色职责(你已说明的部分)

| tab | 每个 agent 的职责 |
| --- | --- |
| Spec | 针对**该 IP**设计、完善设计文档 |
| 验证 | 负责**该 IP**的 UVM 验证 |

| 架构、RTL | 你没展开,drawio 中同样是每 IP 一个 agent |

## 4. 流程顺序(接力关系)

你提到"按顺序",从 tab 排列看整体顺序大概是 Spec → 架构 → RTL → 验证 → 软件,但**你只明确写出了"验证 → 软件"这一跳**。其余相邻角色之间是否也各有一跳,待确认(§6 Q2)。

示例消息:

> "uart 这个 IP 我已经验证完成了,请你开始 uart 这个 IP 的驱动程序开发和 HAL 库开发。"

## 5. 通信约束

1. **只能同 IP 通信**:UART 的验证 agent 只能找 UART 的软件 agent,不能找 GPIO 的任何 agent。drawio 里"通信网络(只允许相同 IP 之间通信)"一框就是这个意思。
2. **通信由 agent 主动发起**:agent 在自己判断"该通知下游了"的时候,自己调用本地 herdr 命令发出消息,而不是由人或中央调度器来转发。
3. **通信拓扑是有限图,不是全连接**:每个 agent 只需要找固定的几个对象(同 IP、相邻角色)。
4. **消息内容是确定的自然语言指令**,不是复杂结构化对象。

## 9. 我对需求本质的理解(请核对)

1. 这是一个"**角色 × IP**"二维矩阵,行是 5 个角色(tab),列是 N 个 IP,每格一个常驻 agent。
2. 通信只沿**列内**(同一 IP)发生,**不沿行**(同一角色的不同 IP)发生。
3. 通信动机是流水线交接:上一个角色完成后,通知同 IP 的下一个角色启动。
4. 通信发起者是 agent 自己,而不是人。
5. 身份(角色+IP)需要在 agent 启动时就确定,并且能被 agent 自己可靠读取。
6. herdr 在这里承担"运行时 + 寻址 + 状态可见"的职责,不承担业务路由规则;"只能同 IP 通信"这条规则大概率需要由我们这一侧来保证(待讨论)。

第 6 点是我的推断,不是已验证事实。

### 12.1 由这些决定推出的需求要点

1. **拓扑是唯一事实源**:谁能给谁发,只由全局拓扑数据结构决定;没有任何旁路。
2. **边是有向的**:允许 `dv→sw`,不代表允许 `sw→dv`;允许 `dv→rtl`(回退)要单独写一条。
3. **同 IP 约束依旧成立**(你最初的需求):只能在同一个 IP 的不同角色之间通信。拓扑负责"哪些角色之间",同 IP 由框架强制。
4. **发送方不能写自由文本**:消息内容由"边 + 模板 + 字段(如 ip)"生成。
5. **模板可动态配置**:模板与拓扑同属配置,变更不需要改代码。
6. **等待 idle 是硬条件**:目标不是 idle 就不发。
