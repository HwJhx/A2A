## Codex 审核(d5a962f)后的修改

Codex 审核结论:阻断 1、应修 6,均已采纳。
- 阻断:脚本用固定会话名,清理时不确认归属,同名会话会被删除。改为每次运行用唯一会话名(带进程号),开始前确认 herdr 会话和 tmux 会话都不存在,只清理本次创建并确认归属的资源。
- 应修:herdr 调用耗时与并发标为采样估计;结论 2、3、5、6 收窄措辞;内存停止条件改为分段等待、阻塞步骤前后都检查;清理失败或有残留进程时运行结果为失败(退出码非零);布局探测拆分失败即停并返回非零。
- 这些修改不改变测量方法,本报告的数据(修改前跑出)仍然有效。

## 结论(N = 10 / 20 / 30)

1. **150 个 agent 撑得住,没有出现瓶颈性的资源压力。** 最低可用内存比例 86%(停止阈值 20%);herdr 服务 143 MB;没有任何错误、丢失、重复、串 IP 或顺序错乱。
2. **本次观测中,投递延迟没有随规模上升。** 所有 IP 同时发送时,入队到送达的 95 分位在 50 / 100 / 150 个 agent 时分别是 1.53 / 1.51 / 1.30 秒(每档 3 轮)。这只说明这三档里没有观察到上升,不能推出更大规模时也不上升。延迟主要由 `herdr agent prompt`(约 0.4 秒,含等待目标进入 working)和假 agent 每条消息 1 秒的忙碌构成。
3. **broker 的线程数和 herdr 并发跟着"同时有消息的目标数"走。** 线程数 = 活跃目标数 + 1,herdr 子进程并发峰值(采样估计)= 活跃目标数(30 个目标同时投递时都是 30 左右)。空转时三档都是每秒一次 `herdr workspace list`、1 分钟 broker CPU 约 0.1 秒。注意:本次各档里活跃目标数和 agent 总数是一起增加的,数据本身不能把两者分开;"与 agent 总数无关"目前只有实现上的依据(broker 只为有待投递消息的目标启动 worker)和空转数据的支持,严格证明需要固定活跃目标数、只改变 agent 总数的对照(列为将来考虑)。
4. **积压 600 条在 27 秒内全部送达,时间由单个目标的串行投递决定。** 每个目标 20 条 × 约 1.35 秒;30 个目标并行。broker 重启恢复 0.06 秒。
5. **唯一的明显瓶颈是 spawn:逐个启动,每个约 4 秒,150 个共 10 分钟。** 原因是在 herdr 0.9.3、这台 VM 上观察到:herdr 识别 pi 后约 3 秒才判定 idle(见下)。改进方向是并行批量 spawn。
6. **本次 150 个假 agent 的负载没有显示必须改用 socket 的证据。** 每次调用起一个 herdr 子进程,并发峰值约 30 个;`agent prompt` 约 0.4 秒,其他调用低于 20 毫秒的采样精度(spawn 诊断里用前后打点测得单次 1–5 毫秒)。没有做 socket 的对照测试,是否改 socket 留到更大规模或真实 agent 暴露问题时再看。

局限:
- 只用了假 agent。真实 fnx 的内存(每个进程远大于假 agent 的约 4.7 MB)、启动时间和处理时间都不同;150 个真实 fnx 能否放进这台 VM 需要另外评估(会调用模型时还涉及接口限流)。
- 延迟终点由轮询得到,精度约 50 毫秒。herdr 调用次数是精确的,但起止时间都由 20 毫秒采样得到,所以单次耗时和并发峰值是估计值,短于 20 毫秒的调用耗时会记成 0(新版 report.json 字段名为 `by_command_sampled_s`)。
- 采样器自身每分钟约 3.5 秒 CPU,比 broker 空转还多,但它是独立进程内的线程,不影响 broker 的数字;herdr 服务和系统的 CPU 数字里不包含它。

## spawn 每个约 4 秒的原因

给 spawn 的每次 herdr 调用计时(4 个假 agent,结果一致):

| 阶段 | 耗时 |
| --- | --- |
| Python 启动、建 pane、改名、启动进程 | 约 0.1 秒(每次 herdr 调用 1–5 毫秒) |
| 等 herdr 识别出 agent(每 0.5 秒轮询) | 约 1.0 秒 |
| **识别后等 `agent wait --until idle/done`** | **约 2.9 秒** |
| 改名 | 0.005 秒 |

每 0.1 秒查一次状态的对照实验:

| 进程 | 状态变化 |
| --- | --- |
| 假 agent(不主动上报) | 0.7 秒 `unknown` → 4.0 秒 `idle` |
| 以 pi 名字运行的 `sleep` | 0.7 秒 `unknown` → 3.9 秒 `idle` |
| 先 `report-agent` 上报 idle | 0.1 秒 `idle` |

结论:在 herdr 0.9.3、这台 VM 上,**这段时间来自 herdr 本身,不是 a2a**——识别出 pi 进程后先标 `unknown`,约 3 秒没有动静才判定 `idle`(样本是 4 个假 agent 加 3 组对照;其他版本或环境未验证)。a2a 的 spawn 必须等到可投递状态才改名、登记,所以每个都要等这段时间;逐个启动时 150 个约 10 分钟。改进方向:先建好并启动所有 pane,再一起等它们变成 idle(并行批量 spawn),留到压测之后做。
