# 阶段 8 测试方案:真实 fnx 规模测试(草案,待用户确认、Codex 审核)

## 1. 目标

阶段 8 的压测用的是假 agent,测的是框架本身的承载能力。这一轮用**真实的 fnx_dv / fnx_sw、真实模型**,按用户的目标规模(同时活跃约 20 个 IP)跑阶段 6 的双向链路,回答压测回答不了的问题:

1. 很多 IP 同时调用模型时,会不会被限流或报错,响应会不会明显变慢;
2. 真实处理时间下,多个 IP 同时进行时投递是否仍然正确、及时(对方忙时排队,空闲后再投);
3. agent 工作时内存涨多少(之前只测了空闲时每个约 98 MB);
4. 每条链路从发起到结束要多久。

## 2. 规模与模型调用量

分两档,**A 档通过并经用户确认后才跑 B 档**:

| 档 | IP 数 | fnx 数 | 预计模型调用 |
| --- | --- | --- | --- |
| A | 5 | 10(dv、sw 各 5) | 约 25 次 |
| B | 20 | 40(dv、sw 各 20) | 约 100 次 |

每个 IP 约 5 次模型调用(依据阶段 6 实测):dv 调用工具 1 次、发送后总结 1 次、收到回复后答"收到"1 次;sw 调用工具 1 次、发送后总结 1 次。模型是两边默认的 sophnet / DeepSeek-Flash。(上一条消息里估计的 60–80 次偏低,以此为准。)

## 3. 拓扑与模板

沿用阶段 6,已经用真实模型验证过:

| 边 | 方向 | 模板 |
| --- | --- | --- |
| `dv_done` | dv → sw | `{ip} ip 我已经完成了uvm验证，你需要对这个{ip} ip进行 驱动程序开发和HAL框架开发。不要真的去做，直接用 a2a_send 回复测试成功或测试失败（二选一）` |
| `sw_test_pass` | sw → dv | `我已经完成了{ip} ip的驱动程序开发，测试成功。你只回复收到即可，不要真的去做` |
| `sw_test_fail` | sw → dv | `我已经完成了{ip} ip的驱动程序开发，测试失败。你只回复收到即可，不要真的去做` |

IP 名为 `ip00` … `ip19`。dv、sw 都以 `--no-builtin-tools` 启动,模型只有 `a2a_send` 一个工具。

## 4. 流程

1. **准备(不调用模型)**
   - 确认 Codex / codex-test 没在用 VM。
   - 新建独立命名会话(名字带进程号,开始前确认不存在;只清理本次创建的资源,沿用压测脚本修好的做法)。
   - 临时安装插件(Codex 审核后修订):
     - 文件名带进程号,例如 `extensions/a2a_scale_<pid>.ts`,不会覆盖已有文件;记录 extensions 目录原来是否存在;
     - 安装前检查目录里所有 `.ts` 文件,只要有别的文件含 `a2a_send` 就中止,不安装;
     - **无论成功还是失败都在结束时删除本次的插件文件**(目录是本次建的且已空就一并删除)。已经启动的 fnx 早已加载插件,删除文件不影响保留下来的现场。
   - 每个 agent 用**各自的临时工作目录**(`work/dv_ip00` 等),这样每个 fnx 的会话记录在单独的目录里,便于逐个取证,也能逐个检查"没有写文件"。
   - 逐个 spawn,启动 broker,记录空闲时的内存。
2. **同时发起(唯一的人工输入)**
   - 用多个线程几乎同时给每个 dv 发开头提示:`假设你已经完成了 <ip> ip 的 UVM 验证，请用 a2a_send 工具通知软件智能体。`
3. **等链路走完**:每个 IP 都要经过 dv 发 `dv_done` → sw 回 `sw_test_pass` / `sw_test_fail` → dv 回复"收到"。单条链路最长等 10 分钟。
4. **取证与核对**(见第 5、6 节)。
5. **收尾**:停 broker、purge、删除会话、删除空的 fnx 会话目录;**fnx 的非空会话记录保留**作为模型调用证据;状态目录保留。插件文件无论成功失败都删除(见第 1 步)。触发停止条件时按第 7 节处理,先保留现场、向用户汇报后再清理。

## 5. 测量

- **每条链路的时间线**(单调时钟 + 审计时间戳对照):发起 → `dv_done` 入队 → 送达 sw → sw 回复入队 → 送达 dv → dv 回到空闲。给出各段与总时长的中位数、95 分位、最大值。
- **投递等待**:sw 的回复入队时 dv 往往还在输出总结,broker 会先记 `WAITING_TARGET`;统计这类等待的次数与时长。
- **模型调用**(Codex 审核后修订):从每个 fnx 的会话记录统计 assistant 消息数、provider / model、token 用量、`stopReason`(非 `toolUse` / `stop` 的视为出错,如限流、超时、接口报错)。
  - **单次调用耗时**:每条 assistant 记录里 `message.timestamp` 是请求开始时刻,外层 `timestamp` 是回复写入时刻,两者之差即单次调用耗时(已在阶段 6 的记录上核实:例如 2.03 秒、1.29 秒)。给出中位数、95 分位、最大值,并和阶段 6 单条链路时的耗时对比,用来判断并发时模型是否变慢。
  - **模型调用并发数**:把所有 fnx 的这些时间段放在一起,统计同一时刻进行中的调用数的峰值。
  - 时间取自同一台 VM 的系统时钟,不同进程之间可比;精度为毫秒。如果某些记录缺这两个字段,该部分只报告端到端耗时,不推断模型侧是否变慢。
  - 本轮不设"明显变慢"的量化阈值,与阶段 6 的对比只作描述性数据(Codex 复核:将来考虑)。
- **内存**:spawn 后空闲时、工作期间峰值(每 0.5 秒采样 MemAvailable 与各 fnx 的 PSS)、全部结束后。
- **broker 与 herdr**:沿用压测的透明包装与采样(调用次数精确,耗时与并发为采样估计)。

## 6. 判定(Codex 审核后修订:框架正确性与模型任务完成度分开)

**(一)框架正确性**——只看框架做的事,与模型是否照指示做无关。任何一条违例都判定**框架失败**,按第 7 节停止:
- 每条**已入队**的消息:发送方、目标、文字都等于"本 IP 的模板"(目标是同 IP 的对端,文字填的是本 IP);
- 每条已入队的消息都只送达一次,没有 `DELIVERY_UNCERTAIN`、`TIMEOUT`、`TARGET_*`、`FAILED` 等异常状态;
- 没有任何消息送到别的 IP;Router 没有出现非预期的拒绝;
- 所有工具调用都是 `a2a_send`(模型只有这一个工具);所有临时工作目录为空。

**(二)模型任务完成度**——按 IP 记录这条链路有没有走完,以及没走完卡在哪一步:
- 走完 = dv 发了 `dv_done`、sw 回了 `sw_test_pass` 或 `sw_test_fail`、dv 最后一条 assistant 消息含"收到";
- 没走完的 IP 记下原因:模型接口出错(`stopReason` 异常)、模型没调用工具、模型多调用了一次工具、超时未完成等。这些归为**模型侧**,与框架问题分开汇报,本身不触发停止(连续报错除外,见第 7 节)。
- 注意:模型多调用一次工具会让该 IP 入队 3 条,这是模型行为;只要每条消息本身正确、各送达一次,框架仍判为正确。
- **调用上限**(Codex 复核补充,防止消息循环让调用量膨胀):
  - 每个 IP 入队的消息不超过 3 条(预期 2 条,最多容许多 1 条);
  - 全部 fnx 的模型调用(assistant 消息)合计不超过预计值的 2 倍(A 档 50 次、B 档 200 次),脚本运行中每 2 秒从会话记录统计一次;
  - 超过任一上限即按第 7 节停止,归为**模型行为异常**(不是框架失败),在报告里单列。

**A 档通过、可以申请进入 B 档的门槛:**
- 框架正确性 100%;
- 模型任务完成度至少 4/5 个 IP,且没走完的 IP 都有明确的模型侧原因;
- 达到门槛后向用户汇报,**经用户确认**才跑 B 档。达不到门槛时也向用户汇报,由用户决定重跑 A 档还是调整。

## 7. 停止条件与停止后的处理(Codex 审核后修订)

**触发条件**(任一):
- 第 6 节(一)框架正确性的任何违例;
- 模型接口连续报错(同一分钟内超过 5 次);
- 单条链路超过 10 分钟没有走完;
- `MemAvailable / MemTotal` < 20%;
- 超过第 6 节的调用上限(某 IP 入队超过 3 条,或模型调用合计超过预计的 2 倍)。

**触发后立即做:**
1. 停止 broker(SIGTERM,按已有的优雅停机:正在进行的那次投递收尾,不再开始新的投递)。broker 停了,就不会再有新消息送进任何 agent,也就不会再触发新的模型调用。
2. 不再给任何 agent 发输入,也不发 Esc 等按键去打断它们;已经在进行中的模型调用让它自然结束(打断会改变现场)。
3. 快照证据:复制审计日志、spool、注册表、broker 日志,并记录所有 fnx 会话记录的路径与大小。
4. 内存相关的触发:快照后如果可用内存继续下降、低于 10%,对所有 agent 执行 `agent stop`(保护 VM),会话记录与状态目录保留;其他情况**保留 agent 运行**,等用户查看。
5. 删除本次的插件文件(不影响已运行的 agent),然后向用户汇报,由用户决定何时清理。

## 8. 实现

- 新脚本 `herdr/a2a/tests/stress/real_fnx_scale.py`。只有同时设置 `A2A_REAL_FNX=1` 并传 `--ips N` 时才会运行,避免误跑调用模型。
- 复用压测脚本的会话归属检查、清理与采样代码思路;不修改 `src/` 下的生产代码。
- 结果写进 `14-stage8-scale-report.md` 新的一节;原始数据(报告 JSON、采样、状态目录、会话记录位置)留在 VM 的 `~/a2a_stage8_real/n<N>/`。

## 9. 约束

- 模型调用只发生在第 4 节第 2–3 步,须用户同意;A 档达到第 6 节门槛并经用户再次确认后才跑 B 档。
- 不动用户的会话和 Codex 的 `a2a_codex_verify`;Codex 用 VM 时不跑。
- 只往 fnx 目录临时加插件文件,不改 fnx 本身;非空的会话记录保留。
