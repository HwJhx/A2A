# 阶段 8 测试方案(第一步):规模压测(草案,待用户确认、Codex 审核)

## 1. 目标

阶段 8 是规模化。第一步先做**压测**,因为它的结果决定后面几项怎么设计(是否改用 socket、动态增删与注册表恢复的做法)。

只用假 agent,**不调用模型**。要回答的问题:

1. herdr 能不能放下目标规模的 pane(5 个角色 × N 个 IP),布局有没有上限;
2. 启动这么多 agent 要多久,herdr 和 broker 占多少 CPU / 内存;
3. 很多 IP 同时发消息时,投递延迟多少,有没有丢失、重复、串 IP;
4. 没有消息时,broker 空转的开销;
5. 积压很多消息时,broker 重启恢复要多久。

压测的产出是**一组数字和一个结论**(能撑到多少、瓶颈在哪),不是"通过 / 不通过"。

## 2. 已知事实

**虚拟机**:15 核 CPU、16 GB 内存(空闲约 15 GB)、磁盘 451 GB 空闲;单进程文件句柄上限 1048576,用户进程数上限 64277。

**broker 的结构**(本方案测的是 Claude 实现 `herdr/a2a` 的 `broker.py` / `delivery.py`):
- 每秒扫描一次队列目录(`policy.py:95` `scan_interval_s = 1.0`;Codex 实现 `a2a_codex` 的默认 0.5 秒,不在本方案范围);只为**有待投递消息**的目标启动 worker 线程,空闲的目标不占线程;
- worker 每次调用 herdr 都是起一个 `herdr` 命令行子进程(`agent wait` 每段最多 2 秒、`agent prompt --wait`);
- 所以开销主要随"同时有消息的目标数"增长,而不是随 agent 总数增长。这需要实测确认。

**布局**(`lifecycle.py`):一个 workspace;每个角色一个 tab;同一角色的各 IP 在该 tab 里向下拆分 pane。30 个 IP 就是一个 tab 里 30 个 pane。herdr 对一个 tab 能拆多少个 pane、pane 最小尺寸,**还没测过**,这是最大的未知数。

## 3. 测试步骤

规模分档:N = 2、10、20、30 个 IP,即 10、50、100、150 个 agent。每档跑完记录数据、清理后再进下一档。任何一档触发第 5 节的停止条件就停下,向用户汇报。

### 3.0 探测 herdr 布局上限(不涉及 a2a)

在独立会话里,按**实际目标布局**探测:一个 workspace、5 个 tab、每个 tab 里连续 `pane split` 到 30 个 pane(共 150 个),每个 pane 里运行一个空闲的假进程。记录:
- 每个 tab 在第几个 pane 失败、报什么错;
- 整个 workspace / 会话有没有总数限制;
- 150 个 pane 都在时,`agent list`、`pane list` 的耗时和 herdr 服务的内存。

- 探测用单独的会话,探测完删除整个会话、确认假进程全部退出,再开始 3.1;3.1 起在全新的会话里由 `a2a agent spawn` 重新启动,不复用探测的 pane,避免探测负载混进后面的数据(Codex 复核补充)。
- 如果一个 tab 放不下 30 个 pane,**先停下来请用户决定布局**(例如每个 tab 只放 10 个 IP,或改为每个 IP 一个 tab),不自行改设计。

### 3.1 批量启动

用 `a2a agent spawn` 逐个启动假 agent(`work` 模式)。记录:

- 每个 agent 的启动耗时、总耗时;
- 启动完成后 herdr 服务进程、broker、全部假 agent 的内存与 CPU;
- `a2a agent list` 的耗时(它要逐个查 herdr)。

### 3.2 空转开销

broker 运行、没有任何消息,观察 60 秒:broker 的 CPU、每秒起的子进程数。

### 3.3 多 IP 同时投递

每个 IP 的 dv(`script:dv_done`,带同步屏障)同时发一条 `dv_done`,即 N 条消息发往 N 个不同目标。记录:

- 两个延迟指标,各给出中位数、95 分位、最大值,都用**单调时钟**(Linux 的 CLOCK_MONOTONIC 全系统共享,假 agent 和压测脚本的读数可以直接相减):
  - **入队到送达**(主指标):假 agent 在 `a2a send` 成功返回的那一刻记下单调时钟时间,作为起点(比 Router 实际写入晚几毫秒,即 send 命令退出的时间,报告里注明);
  - **放开屏障到送达**:从压测脚本创建屏障文件算起,包含各 agent 执行 `a2a send` 的时间,反映"所有 IP 同时发起"时的端到端耗时;
  - 终点都是压测脚本每 50 毫秒轮询 spool、首次看到 DELIVERED 的时间(精度约 50 毫秒,报告里注明)。审计时间戳只用来关联核对,不作延迟主口径,避免系统校时造成偏差(Codex 复核补充);
- 投递期间 broker 的线程峰值、同时存在的 `herdr` 子进程峰值、CPU;
- 正确性:沿用阶段 7 的 `assert_traffic` 思路,入队记录恰好 N 条、每条只送达一次、每个 sw 只收到本 IP 的文字。
- 每档跑 3 轮,报告样本数与分位数的算法(最近秩法);N = 2、10 的样本少,只作初步观察,不下结论。

### 3.4 单目标连发

同一个 dv 连发 20 条到同一个 sw,跑 3 轮。提交方式:broker 运行中,假 dv 收到一次触发后**串行**执行 20 次 `a2a send`(上一条返回再发下一条);假 agent 为此新增 `burst:<边>:<次数>` 模式。记录总耗时和每条延迟,确认按 queue_seq 顺序送达、不交织。

### 3.5 积压后重启

broker 停止时制造积压,再启动 broker。积压量是**独立参数**,不和 N 绑定:先每个 IP 的 dv 各发 3 条,再加一档大积压(例如每个 IP 各发 20 条,N = 30 时 600 条)。记录:
- 启动恢复耗时、全部送达耗时,并确认顺序与次数;
- 积压前后 spool 目录、`done/` 目录和审计文件的大小与文件数。
本步结论只针对所测积压量;审计和 `done/` 长期增长对恢复的影响,列为将来考虑。

## 4. 实现方式

- 新增 `tests/stress/stress_scale.py`:独立脚本,不放进单元测试套件,只有设置 `A2A_STRESS=1` 才会运行。参数是规模 N 和要跑的步骤。
- 资源采样:每 0.5 秒读 `/proc`,写进 CSV:
  - 系统的 `MemAvailable`,作为内存结论的主口径;
  - herdr 服务、broker 的 CPU 时间和 PSS(`/proc/<pid>/smaps_rollup`,按比例分摊共享内存);假 agent 只报 PSS 合计,不用 RSS 相加,避免重复计算共享内存;
  - 采样器自身的 CPU 时间,用来估计测试工具的开销。
- `herdr` 子进程:采样会漏掉短命进程,所以 broker 改用一个包装脚本作 herdr 程序(`a2a broker run --herdr-bin <包装脚本>`,已有的隐藏参数)。包装脚本必须**完全透明**(Codex 复核补充):
  - 只做一件事:往**独立日志文件**追加一行(单调时钟时间、pid、参数),然后 `exec` 真正的 herdr。用 `exec` 而不是起子进程,所以 pid 不变,参数、stdout / stderr、退出码、信号(包括 HerdrClient 超时时的 kill)都原样作用在 herdr 本身,不会改变结果分类和投递行为;
  - 结束时间由采样器以 20 毫秒间隔检查这些 pid 是否还在得到(精度约 20 毫秒);
  - 由此得到调用次数(精确)、并发峰值和每类命令耗时(精度 20 毫秒)。资源类数值标明是采样值。
- 每档结果写进 `herdr/claude/14-stage8-scale-report.md`:表格 + 结论。
- 复用阶段 7 的假 agent `script` 模式和屏障。

## 5. 安全与停止条件

- 使用独立命名会话,每档结束都 purge agent、删除会话;不动用户和 Codex 的会话。
- **停止时的收尾**:触发停止条件或测试异常时,先停 broker,再 purge 本次会话的所有 agent、删除会话、确认没有残留进程,然后再汇报。
- **停止条件**(任一触发就停下汇报):`MemAvailable / MemTotal` 低于 20%(这台 VM 约 3.2 GB);herdr 命令超时或服务无响应;消息丢失、重复或串 IP;启动失败。
- Codex 的 `a2a_codex_verify` 会话也在这台 VM 上。压测会占用资源,可能影响 Codex 同时进行的测试;**压测开始前先确认 Codex 没在跑测试**。
