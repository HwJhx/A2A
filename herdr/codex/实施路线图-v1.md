# Herdr + Pi 多智能体编排实施路线图

> 版本：v1  
> 目标：从最小可验证闭环逐步扩展到动态、多 IP、多 tab、多 agent 系统。
> 进度更新：2026-10-09。状态按实际验证结果记录：通过为 ✅，已执行但未通过为 ❌，未验证保持空白。

## 总体路线

需求定稿 → VM 环境探测 → Python HerdrClient → 拓扑/身份/Registry → Router/模板 → Delivery Broker → 接入 fnx_dv/fnx_sw → 动态拓扑与规模化

建议分为 8 个阶段。

## 阶段 1：需求和通信协议定稿

确认以下规则：

- 五个角色码：spec、arch、rtl、dv、sw（显示名可使用 architecture、verification、software 等）。
- agent 身份由 project_id、ip_id、role、agent_id 构成。
- 通信只能发生在同项目、同 IP 的 agent 之间。
- 允许的通信边是有向边，未配置的边一律拒绝。
- 消息只能由固定模板生成，agent 不能自由指定目标 IP、source 或完整消息文本。
- `idle` 与 `done` 均为 READY；`done` 不会自动变回 `idle`，等待必须同时接受两者。
- 目标 `blocked` 立即失败，不排队；`unknown` 不视为 READY，等待至超时失败。
- 明确是否需要持久化、重试、去重和审计。

阶段产物：拓扑配置（通信边与模板同置于 `edges[].template`）、协议文档；不单独维护模板文件。

## 阶段 4：拓扑、身份和 Registry

业务身份示例：

project_id = soc_a
ip_id = uart
role = dv
agent_id = dv_uart

运行时 registry 保存稳定业务 ID 到动态 Herdr 地址的映射：

- workspace_id
- tab_id
- pane_id
- agent_name
- status
- session

原则：

- agent_id 是稳定身份，当前格式为 `{role}_{ip}`（如 `dv_uart`）；当前单项目 Registry 不重复添加 project 前缀。
- pane_id 是动态位置。
- 重命名不改变业务身份。
- pane 重建后只更新 registry。
- 同一 project_id + ip_id + role 不允许重复注册。
- 发送消息前必须通过 registry 解析当前目标 pane。

## 阶段 5：Router 和固定消息模板

agent 侧只调用：

a2a send dv_done

路由边示例：

- dv_done：verification → software，模板为“{ip}已完成UVM验证，请执行驱动程序和HAL框架开发。”
- dv_to_rtl_fix：verification → rtl，模板为“{ip}验证发现RTL问题，请检查并修复。”

鉴权顺序：

1. 从 HERDR_PANE_ID 获取发送位置。
2. 用 pane ID 与 registry 交叉验证发送方身份。
3. 确认 edge_id 存在且方向正确。
4. 根据发送方 ip_id 自动推导目标 agent。
5. 强制确认 source.ip_id 等于 target.ip_id。
6. 用固定模板生成消息。
7. 写入持久队列。
8. 进入 Delivery Broker。

任何一步失败，都不执行 Herdr 发送命令。

必须拒绝：UART verification → SPI software、跨项目通信、未配置角色边、不存在目标、伪造 source、伪造 ip、自由文本消息。

## 阶段 6：Delivery Broker

目标是：目标忙碌时等待，并发发送时避免交织和重复投递。

状态归一化：

- idle：可以发送
- done：可以发送（READY，与 idle 同级）
- working：等待
- blocked：立即返回失败，不排队、不自动批准
- unknown：不能投递；等待至超时后失败
- 不存在：尝试恢复或失败

消息状态：

CREATED → ROUTED → WAITING_TARGET → DISPATCHING → DELIVERED

异常状态：TARGET_BLOCKED、TIMEOUT、RETRYING、FAILED。

并发控制：

- 每个目标 agent 一把锁。
- 每个目标一条持久队列。
- 每条消息一个 message_id。

投递流程：

1. 获取目标 agent 锁。
2. 从队列取最早消息。
3. 等待目标 idle/done。
4. 再次读取并确认状态。
5. 调用 agent prompt。
6. 记录 delivered 和 Herdr 返回值。
7. 释放锁。

Herdr 的 agent wait 负责服务端状态等待，但不能保证“等待完成”和“发送 prompt”之间不会被另一个发送者插入，因此仍需要目标级锁或中心化 broker。
