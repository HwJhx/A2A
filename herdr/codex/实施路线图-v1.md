# Herdr + Pi 多智能体编排实施路线图

> 版本：v1  
> 目标：从最小可验证闭环逐步扩展到动态、多 IP、多 tab、多 agent 系统。

## 总体路线

需求定稿 → VM 环境探测 → Python HerdrClient → 拓扑/身份/Registry → Router/模板 → Delivery Broker → 接入 fnx_dv/fnx_sw → 动态拓扑与规模化

建议分为 8 个阶段。

## 阶段 1：需求和通信协议定稿

确认以下规则：

- 五个角色：spec、architecture、rtl、verification、software。
- agent 身份由 project_id、ip_id、role、agent_id 构成。
- 通信只能发生在同项目、同 IP 的 agent 之间。
- 允许的通信边是有向边，未配置的边一律拒绝。
- 消息只能由固定模板生成，agent 不能自由指定目标 IP、source 或完整消息文本。
- 明确 done 是否和 idle 一样可投递。
- 明确目标 blocked 时保留队列还是超时失败。
- 明确是否需要持久化、重试、去重和审计。

阶段产物：a2a_topology.yaml、a2a_message_templates.yaml、a2a_protocol.md。

## 阶段 2：VM 环境探测

在 Orb VM 192.168.139.41 的命名 Herdr session 中验证：

1. fnx_dv 是否能被 Herdr 识别为验证 agent。
2. fnx_sw 是否能被 Herdr 识别为软件 agent。
3. A2A_PROJECT_ID、A2A_IP、A2A_ROLE 是否能传入 agent。
4. 跨 tab 的 agent prompt 是否可用。
5. agent wait 对 idle、done、working、blocked 的实际行为。
6. agent read 对 Pi 全屏终端的读取行为。
7. Herdr CLI 和 Socket API 的实际参数。
8. Herdr server 重启后 registry 如何恢复。

最小实验：命名 session a2a_test，创建 workspace soc-a-test、verification tab、software tab、UART 的 fnx_dv 和 fnx_sw。

阶段验收：两个 agent 能启动、身份可读取、跨 tab 通信成功、目标忙碌时不会立即插入第二条消息，并且实验不影响主 session。

## 阶段 3：Python HerdrClient

先把 Herdr CLI 封装成 Python API，暂时不加入业务路由。

建议目录：

- herdr_client.py：Herdr CLI/Socket 封装
- models.py：数据模型
- errors.py：异常
- cli.py：命令行入口
- tests/：测试

第一版 API 应覆盖：

- create/delete/rename_workspace
- create/delete/rename_tab
- create/delete/rename_pane
- start_agent
- get_agent
- read_agent
- send_prompt
- wait_agent

第一版用 Python subprocess 调 Herdr CLI；后续再对事件订阅和长时间等待接入 Socket API。

## 阶段 4：拓扑、身份和 Registry

业务身份示例：

project_id = soc-a  
ip_id = uart  
role = verification  
agent_id = soc-a/uart/verification

运行时 registry 保存稳定业务 ID 到动态 Herdr 地址的映射：

- workspace_id
- tab_id
- pane_id
- agent_name
- status
- session

原则：

- agent_id 是稳定身份。
- pane_id 是动态位置。
- 重命名不改变业务身份。
- pane 重建后只更新 registry。
- 同一 project_id + ip_id + role 不允许重复注册。
- 发送消息前必须通过 registry 解析当前目标 pane。

## 阶段 5：Router 和固定消息模板

agent 侧只调用：

a2a send dv_done

agent 不提供 source、target-ip、target-pane、message 参数。

路由边示例：

- dv_done：verification → software，模板为“{ip}已完成UVM验证，请执行驱动程序和HAL框架开发。”
- dv_to_rtl_fix：verification → rtl，模板为“{ip}验证发现RTL问题，请检查并修复。”

鉴权顺序：

1. 从 HERDR_PANE_ID 获取发送位置。
2. 用 pane ID 与 registry 交叉验证发送方身份。
3. 确认 edge_id 存在且方向正确。
4. 根据发送方 ip_id 自动推导目标 agent。
5. 强制确认 source.ip_id 等于 target.ip_id。
6. 用固定模板生成消息。
7. 写入持久队列。
8. 进入 Delivery Broker。

任何一步失败，都不执行 Herdr 发送命令。

必须拒绝：UART verification → SPI software、跨项目通信、未配置角色边、不存在目标、伪造 source、伪造 ip、自由文本消息。

## 阶段 6：Delivery Broker

目标是：目标忙碌时等待，并发发送时避免交织和重复投递。

状态归一化：

- idle：可以发送
- done：建议视为可以发送
- working：等待
- blocked：保留队列并告警，不自动批准
- unknown：等待或转人工
- 不存在：尝试恢复或失败

消息状态：

CREATED → ROUTED → WAITING_TARGET → DISPATCHING → DELIVERED

异常状态：TARGET_BLOCKED、TIMEOUT、RETRYING、FAILED。

并发控制：

- 每个目标 agent 一把锁。
- 每个目标一条持久队列。
- 每条消息一个 message_id。

投递流程：

1. 获取目标 agent 锁。
2. 从队列取最早消息。
3. 等待目标 idle/done。
4. 再次读取并确认状态。
5. 调用 agent prompt。
6. 记录 delivered 和 Herdr 返回值。
7. 释放锁。

Herdr 的 agent wait 负责服务端状态等待，但不能保证“等待完成”和“发送 prompt”之间不会被另一个发送者插入，因此仍需要目标级锁或中心化 broker。

## 阶段 7：接入 fnx_dv 和 fnx_sw

验证 agent 完成 UART UVM 验证后调用：

a2a send dv_done

框架执行：

识别发送方 soc-a/uart/verification → 查找 dv_done → 推导目标 soc-a/uart/software → 等待 fnx_sw idle/done → 渲染固定模板 → 发送 → 记录 message_id 和审计日志。

软件 agent 收到后：

1. 校验消息来源。
2. 校验 IP 是 UART。
3. 读取验证报告和覆盖率报告。
4. 启动 UART 驱动和 HAL 开发流程。
5. 按允许的边发送后续事件。

## 阶段 8：动态拓扑与规模化

最后再加入：

- 批量创建五个职责 tab。
- 至少三个 tab 默认对全部 IP 创建 agent。
- 动态新增和删除 IP agent。
- 动态暂停、恢复和重命名。
- registry 自动恢复。
- Socket 事件订阅。
- 全局 Monitor。
- GUI 状态同步。
- 150 个 agent 的资源压测。

规模递增建议：

1 workspace + 2 tabs + 1 IP + 2 agents  
→ 2 tabs + 2 IPs + 4 agents  
→ 5 tabs + 2 IPs + 10 agents  
→ 5 tabs + 全部 IP

重点压测 VM 内存、CPU、Pi 进程数、模型并发、broker 吞吐、状态事件丢失和 Herdr server 重启恢复。

## 第一阶段最小闭环

Workspace soc-a-test：

- verification tab：UART / fnx_dv
- software tab：UART / fnx_sw

只配置一条边：verification → software。

只配置一个模板：{ip}已完成UVM验证，请执行驱动程序和HAL框架开发。

必须验证：

1. 两个 agent 可由 Python 框架创建和登记。
2. agent 能可靠获得 project、IP、role。
3. a2a send dv_done 能定位正确目标。
4. 目标忙碌时消息进入等待队列。
5. 目标变为 idle/done 后消息才发送。
6. UART → SPI 被拒绝。
7. 未配置角色边被拒绝。
8. 并发发送不会交织。
9. broker 重启后消息不丢失。
10. agent 不需要直接执行 herdr agent prompt。

## 最终分层架构

Pi 二次开发 Agent  
↓ a2a send <edge_id>  
Python Agent Orchestrator  
↓ Identity、Registry、Router、Template Renderer、Delivery Broker、Lock/Queue、Audit Journal  
HerdrClient  
↓ Herdr CLI / Socket API  
Herdr Server  
↓ Workspace / Tab / Pane / Process

职责边界：

- Pi Agent：完成 Spec、RTL、UVM、驱动、HAL 等专业任务。
- Python Orchestrator：负责身份、路由、模板、队列、状态、重试和审计。
- Herdr：负责终端布局、agent 进程、状态读取和 prompt 投递。
