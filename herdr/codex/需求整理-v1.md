# Herdr + Pi 多智能体协作需求整理

> 版本：v1（待用户确认）  
> 目的：先统一业务需求、对象层级和通信语义；本稿暂不锁定最终代码实现。

## 1. 总体目标

在一个 SoC 项目中，使用 Herdr 管理多个基于 Pi 二次开发的异构智能体。

每个智能体只负责一个固定的 Chip IP 和一种固定的工程职责。不同职责的智能体之间可以协作，但通信必须遵守“同一个 IP 才能通信”的路由约束。

典型流程是：

```text
UART 的 Spec 智能体
        ↓
UART 的架构智能体
        ↓
UART 的 RTL 智能体
        ↓
UART 的验证智能体 ──完成 UVM 验证──→ UART 的软件智能体
                                      ↓
                            生成 UART 驱动和 HAL 框架
```

这里的 `UART` 是业务身份，不能因为 Herdr 的 pane、tab 或 agent 重启、重命名而改变。

## 2. 业务对象与 Herdr 对象的映射

用户当前希望使用以下映射：

| 业务概念 | Herdr 概念 | 含义 |
| --- | --- | --- |
| 项目 A 根目录 | Workspace | 一个完整 SoC 项目或一个项目工作上下文 |
| Spec、架构、RTL、验证、软件等逻辑分组 | Tab | 项目内按职责划分的工作视图 |
| 某个职责下负责某个 IP 的智能体 | Pane 中运行的 Agent | 一个基于 Pi 二次开发的长期运行智能体 |
| UART、SPI、I2C 等 Chip IP | Agent 的固定业务身份 | 智能体从启动到退出始终负责同一个 IP |
| “验证完成”或“开始软件开发” | Agent 事件/任务消息 | 驱动后续智能体进入下一阶段 |

以 30 个 IP 为例，期望的运行结构大致是：

```text
Workspace: SoC 项目 A
├── Tab: Spec
│   ├── Pane/Agent: UART
│   ├── Pane/Agent: SPI
│   └── ... 共 30 个 IP agent
├── Tab: 架构
│   └── ... 共 30 个 IP agent
├── Tab: RTL
│   └── ... 共 30 个 IP agent
├── Tab: 验证
│   ├── Pane/Agent: UART
│   ├── Pane/Agent: SPI
│   └── ... 共 30 个 IP agent
└── Tab: 软件
    ├── Pane/Agent: UART
    ├── Pane/Agent: SPI
    └── ... 共 30 个 IP agent
```

因此，一个完整项目最多可能同时运行约 `5 × 30 = 150` 个 IP agent。

## 3. Agent 的身份模型

需求中实际上存在两类身份，需要分开：

### 3.1 Herdr 运行身份

Herdr 需要知道 agent 当前运行在哪个：

- workspace
- tab
- pane
- Herdr session/server

这些是运行时定位信息，可能因为 pane 移动、tab 重排、server 恢复而变化。

### 3.2 业务身份

每个 Pi agent 必须有稳定的业务身份：

```text
project_id = soc-a
ip_id       = uart
role        = verification
agent_id    = soc-a/uart/verification
```

其中：

- `project_id`：所属项目，例如 `soc-a`。
- `ip_id`：固定负责的 Chip IP，例如 `uart`。
- `role`：职责类型，例如 `spec`、`architecture`、`rtl`、`verification`、`software`。
- `agent_id`：由业务身份生成的稳定标识，不应依赖 `w1:p3` 这种临时 pane ID。

因此，用户第（4）个担心点的核心答案是：

> Agent 不能通过当前 tab 名称或 pane 名称来判断自己的业务身份；它应该在启动时被显式注入 `project_id`、`ip_id` 和 `role`，并把这些身份作为自己的固定配置或启动环境变量。

Herdr 的 workspace/tab/pane ID 负责“我现在在哪里”，Pi agent 的业务元数据负责“我是谁、我负责什么”。

## 4. 通信约束

### 4.1 基本约束

任意两个 agent 只有在以下条件满足时才允许通信：

```text
source.project_id == target.project_id
source.ip_id      == target.ip_id
source.role       != target.role
```

也就是说：

- 同一个项目内可以通信。
- 必须是同一个 Chip IP。
- 通常发生在不同职责之间。
- 不允许 UART 验证 agent 把任务发给 SPI 软件 agent。
- 不允许 UART agent 把任务发给另一个项目的 UART agent，除非未来明确开放跨项目通信。

### 4.2 允许的通信图

通信不是任意全连接，而是一个有限有向图。

当前需求中的主要边包括：

```text
Spec → 架构 → RTL → 验证 → 软件
```

每条边都应由系统配置明确声明。例如：

```text
verification → software : UVM 验证完成通知
rtl          → verification : RTL 基线就绪通知
architecture  → rtl        : 架构设计完成通知
spec          → architecture: Spec 评审完成通知
```

“同 IP”是第一层路由条件；“允许的角色边”是第二层路由条件。

例如：

```text
允许：soc-a/uart/verification → soc-a/uart/software
拒绝：soc-a/uart/verification → soc-a/spi/software
拒绝：soc-a/verification      → soc-b/uart/software
是否允许：soc-a/uart/software  → soc-a/uart/verification
```

最后一项是否允许，需要由具体工作流定义；默认建议使用事件方向约束，而不是允许任意双向通信。

## 5. 典型业务场景

当 `soc-a/uart/verification` 完成 UVM 验证后，它需要发出一条结构化业务消息，语义类似：

```text
source:      soc-a/uart/verification
target:      soc-a/uart/software
event_type:  verification.completed
ip_id:       uart
message:     uart 这个 IP 已完成 UVM 验证，请开始驱动程序和 HAL 框架开发。
artifacts:   验证报告、覆盖率报告、日志路径
```

软件 agent 收到后，应：

1. 验证消息来源确实是 `soc-a/uart/verification`。
2. 校验 `ip_id` 是 `uart`。
3. 校验当前事件允许从 `verification` 流向 `software`。
4. 读取验证报告、覆盖率报告等 artifact。
5. 将自身状态从等待状态切换到软件开发状态。
6. 记录该事件，避免重复消费造成重复启动任务。

这里的自然语言通知可以保留，但正式路由不应只依赖自然语言中的“uart”字符串；应该同时携带结构化身份字段。

## 6. 对三个技术问题的需求化表达

### 6.1 是否需要一开始就拉起全部 agent

期望支持两种启动模式：

#### 模式 A：完整项目启动

根据项目配置，一次创建：

- 一个 workspace。
- 五个职责 tab。
- 每个 tab 下每个 IP 对应的 pane。
- 每个 pane 中对应的 Pi agent。

例如 30 个 IP、5 个职责，需要初始化约 150 个 agent。

#### 模式 B：按需启动

只启动当前阶段需要的 agent。例如先启动 Spec 和架构 agent，等工作推进到验证阶段，再创建验证 agent。

两种模式都应使用同一个项目配置文件，避免手动启动时身份和路由信息不一致。

Herdr 本身需要承担 workspace、tab、pane 和 agent 启动编排；项目配置和 Pi agent 启动参数则负责决定“启动哪些 agent、每个 agent 负责哪个 IP”。

### 6.2 是否可以命名 tab 和 pane

需求希望：

- Tab 使用职责名，例如 `spec`、`architecture`、`rtl`、`verification`、`software`。
- Pane 使用 IP 名或带职责的 IP 名，例如 `uart` 或 `verification-uart`。
- Agent 使用稳定业务名，例如 `soc-a-uart-verification`。

但需求不应只依赖 tab/pane 的显示名称来路由，因为显示名称可能被用户修改，pane ID 也可能在移动或重建后变化。

推荐同时保存以下映射：

```text
business_agent_id: soc-a/uart/verification
workspace_id:      w1
tab_id:            w1:t4
pane_id:           w1:p27
agent_name:        soc-a-uart-verification
```

通信时优先使用 `business_agent_id` 查找当前的 `pane_id`，再通过 Herdr CLI 或 Socket API 发送消息。

### 6.3 是否允许 agent 自己调用 Herdr API 发消息

需求明确希望支持：

```text
验证 agent 完成任务
  → agent 自己调用本地 Herdr CLI/API
  → 找到相同 IP 的软件 agent
  → 发送 verification.completed
```

该模式需要满足：

1. Pi agent 能访问 Herdr CLI 或本地 Socket API。
2. agent 启动环境包含自己的业务身份。
3. agent 能访问一个受控的路由查询或消息发送工具。
4. 路由层验证 source、target、ip_id 和允许的 role edge。
5. 发送结果可确认、失败可重试，并且不会重复创建任务。

业务上更推荐 agent 调用一个项目级封装命令，例如：

```bash
soc-agent-msg send \
  --event verification.completed \
  --ip uart \
  --target-role software \
  --message "uart 已完成 UVM 验证，请开始驱动程序和 HAL 库开发"
```

而不是让每个 agent 自己拼接底层 `herdr agent prompt <pane-id> ...`。封装命令内部再完成：

```text
业务身份校验
→ 同 IP 校验
→ 角色边校验
→ agent_id 到 pane_id 解析
→ 调用 Herdr agent prompt/socket API
→ 写入事件日志
```

这样可以防止 agent 因为猜错 pane ID 或自然语言写错 IP 而把消息发错对象。

## 7. 启动时身份注入的要求

每个 Pi agent 启动时应获得一份不可歧义的身份配置，例如：

```bash
SOC_PROJECT_ID=soc-a \
SOC_IP_ID=uart \
SOC_AGENT_ROLE=verification \
SOC_AGENT_ID=soc-a/uart/verification \
herdr agent start soc-a-uart-verification \
  --kind pi \
  --pane <pane-id>
```

或者由 Pi agent 读取项目根目录下的身份文件：

```text
project-a/.agents/identity.yaml
```

示例：

```yaml
project_id: soc-a
ip_id: uart
role: verification
agent_id: soc-a/uart/verification
allowed_outgoing_edges:
  - software
```

身份信息至少需要包含：

- `project_id`
- `ip_id`
- `role`
- `agent_id`
- 当前 agent 允许发送消息的目标角色
- 当前 agent 允许接收的事件类型

## 8. 对现有需求的统一理解

我目前对你的需求理解为：

> 你要构建一个以 Herdr 为运行时终端编排器、以 Pi 二次开发 agent 为工作单元、以 Chip IP 为业务隔离键、以职责阶段为有限有向通信图的 SoC 多智能体协作系统。

其中：

- Workspace 表示一个 SoC 项目。
- Tab 表示一个工程职责分组。
- Pane 表示一个正在运行的 IP 专属 agent。
- Agent 的稳定身份不是 pane ID，而是 `项目 + IP + 职责`。
- Herdr 负责创建和管理运行时对象，并提供本地 agent 通信能力。
- 项目级路由层负责把稳定业务身份映射到当前 Herdr pane，并限制通信只能沿允许的同 IP 有向边发生。
- Agent 可以在完成阶段任务后主动发起事件，通知同 IP 的下游 agent。
- 消息除了自然语言，还应包含结构化事件、源身份、目标身份、IP、artifact 和幂等信息。

## 9. 需要你确认的关键点

下面这些点会影响下一版设计，但不影响当前需求理解：

1. 五个 tab 是否固定为 `Spec、架构、RTL、验证、软件`？
2. 通信图是否固定为 `Spec → 架构 → RTL → 验证 → 软件`，还是允许某些阶段回退或双向通信？
3. Agent 是否必须一次性启动全部 IP，还是允许按阶段按需启动？
4. 一个 IP 在同一职责下是否永远只有一个 agent？
5. 是否允许同一个 IP 在多个 workspace 或多个 Herdr session 中同时存在？
6. 事件是否需要持久化、重试、去重和审计？
7. agent 之间传递的是纯文本，还是必须携带验证报告、覆盖率报告、代码路径等 artifact？
8. 是否需要一个独立的全局 Monitor agent 负责观察所有 IP 的状态，但不参与业务任务通信？
