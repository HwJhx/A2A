## 1. 本次需求的归纳

在 v1 的基础上，本次需求增加四个核心约束：

1. 五个 tab 中至少三个 tab 对全部 IP 都有常驻 agent，但运行过程中允许动态创建、删除和重命名 workspace、tab、pane、agent。
2. tab 之间的通信关系不是固定的；除了“验证 → 软件”之外，其他角色之间也可能通信，允许边由 workspace 内的数据结构配置。
3. 发送消息时，如果目标 agent 不是可接收状态，需要等待目标变为可接收状态，并具备轮询、超时、重试和失败记录。
4. agent 可以自己调用 Herdr CLI 或本地 API 发起通信，但消息必须经过统一路由校验。

## 3. 目标运行模型

```text
一个 Herdr Session
└── Workspace：项目 A
    ├── Tab：spec
    │   ├── Pane/Agent：soc-a/uart/spec
    │   └── ...
    ├── Tab：architecture
    │   └── ...
    ├── Tab：rtl
    │   └── ...
    ├── Tab：verification
    │   ├── Pane/Agent：soc-a/uart/verification
    │   └── ...
    └── Tab：software
        ├── Pane/Agent：soc-a/uart/software
        └── ...
```

至少三个角色默认对全部 IP 创建 agent；其余角色可以对全部 IP 启动、只对指定 IP 启动，或在工作流进入该阶段时按需启动。因此，agent 数量是动态拓扑，不是固定常量。

## 4. 业务身份与 Herdr 运行身份必须分离

每个 agent 有两套身份：

### 4.1 Herdr 运行身份

- session/server
- workspace ID
- tab ID
- pane ID
- Herdr agent name

这些信息可能因 pane 移动、重建、重启而变化。

### 4.2 业务身份

```text
project_id = soc-a
ip_id       = uart
role        = verification
agent_id    = soc-a/uart/verification
```

`agent_id` 是稳定业务身份，不应依赖 `w1:p3` 这类临时 pane ID。

结论：

> Agent 不能通过当前 tab 名称或 pane 名称判断自己的业务身份；启动时必须显式注入 project、IP 和 role。Herdr ID 表示“我现在在哪里”，业务元数据表示“我是谁、我负责什么”。

建议启动时注入：

```bash
SOC_PROJECT_ID=soc-a \
SOC_IP_ID=uart \
SOC_AGENT_ROLE=verification \
SOC_AGENT_ID=soc-a/uart/verification \
fnx_dv
```

## 5. Workspace 配置数据结构

建议以业务身份为中心保存项目配置：

```yaml
project:
  id: soc-a

  herdr_session: default

roles:
  - id: spec
    label: Spec
    default_startup: all_ips
  - id: architecture
    label: 架构
    default_startup: all_ips
  - id: rtl
    label: RTL
    default_startup: all_ips
  - id: verification
    label: 验证
    default_startup: all_ips
  - id: software
    label: 软件
    default_startup: all_ips

ips:
  - id: uart
    display_name: UART
  - id: spi
    display_name: SPI

agents:
  - id: soc-a/uart/verification
    project_id: soc-a
    ip_id: uart
    role: verification
    executable: fnx_dv
    startup: persistent
  - id: soc-a/uart/software
    project_id: soc-a
    ip_id: uart
    role: software
    executable: fnx_sw
    startup: persistent

routes:
  - from_role: verification
    to_role: software
    ip_scope: same
    events:
      - verification.completed
```

运行时还需要一个 registry，把稳定业务 ID 映射到当前 Herdr 地址：

```json
{
  "soc-a/uart/verification": {
    "project_id": "soc-a",
    "ip_id": "uart",
    "role": "verification",
    "workspace_id": "w1",
    "tab_id": "w1:t4",
    "pane_id": "w1:p27",
    "agent_name": "soc-a-uart-verification",
    "agent_status": "idle",
    "session": "default"
  }
}
```

pane 被移动、删除后重建或 Herdr 恢复时，只更新 registry，不改变业务 agent ID。

## 6. Python 编排 API

建议新增一个独立的 Python 包：

```text
herdr-orchestrator/
├── pyproject.toml
├── src/herdr_orchestrator/
│   ├── herdr_client.py       # Herdr CLI/Socket 封装
│   ├── topology.py           # workspace/tab/pane/agent 拓扑
│   ├── identity.py           # project/ip/role 身份
│   ├── routing.py            # 有向图和权限校验
│   ├── registry.py           # 业务 agent 到 pane 的映射
│   ├── dispatcher.py         # 发送、等待、重试
│   ├── lifecycle.py          # 创建、删除、重命名、恢复
│   └── cli.py                # 给 Pi agent 调用的命令
└── config/
    └── soc-a.yaml
```

第一阶段的 Python API 应覆盖：

```python
class HerdrClient:
    def create_workspace(self, cwd: str, label: str): ...
    def delete_workspace(self, workspace_id: str): ...
    def rename_workspace(self, workspace_id: str, label: str): ...

    def create_tab(self, workspace_id: str, label: str): ...
    def delete_tab(self, tab_id: str): ...
    def rename_tab(self, tab_id: str, label: str): ...

    def create_pane(self, tab_id: str, direction: str = "right"): ...
    def delete_pane(self, pane_id: str): ...
    def rename_pane(self, pane_id: str, label: str): ...

    def start_agent(self, pane_id: str, name: str, kind: str, env: dict): ...
    def get_agent(self, target: str): ...
    def read_agent(self, target: str, lines: int = 80): ...
    def send_prompt(self, target: str, prompt: str): ...
```

底层建议分两阶段：

- 第一阶段用 `subprocess` 调 Herdr CLI，便于调试。
- 第二阶段对长时间等待、事件订阅和批量操作使用 Herdr Socket API。

Herdr 原生支持 workspace、tab、pane 的创建/删除/重命名，以及 pane split、agent start、agent prompt、agent read、agent wait；`agent start` 需要已经存在且处于 shell prompt 的 pane，不能替代 pane 创建。

## 7. 有限有向图路由

除了“验证 → 软件”，其他角色之间也可以通信，但必须显式配置允许边：

```yaml
routes:
  - from_role: verification
    to_role: software
    ip_scope: same
    events: [verification.completed]

  - from_role: verification
    to_role: rtl
    ip_scope: same
    events: [verification.regression_failed]

  - from_role: software
    to_role: verification
    ip_scope: same
    events: [software.driver_ready]
```

发送前按顺序校验：

```text
1. source agent 是否已注册
2. target agent 是否存在
3. source.project_id == target.project_id
4. source.ip_id == target.ip_id
5. source role、target role、event_type 是否命中允许边
6. message_id 是否已发送过
7. 目标状态是否允许发送
```

默认策略：

- 未配置的边一律拒绝。
- `ip_scope: same` 强制校验 `ip_id` 相同。
- agent 不应直接绕过路由层调用底层 `herdr agent prompt` 作为正式业务通信。
- 所有拒绝、发送、重试和超时都写入审计日志。

## 8. idle 等待和消息调度

Herdr 状态在 Python 层归一化：

| Herdr 状态 | 调度含义 |
| --- | --- |
| `idle` | 可以发送 |
| `done` | 视为可以发送 |
| `working` | 等待，不发送新的 prompt |
| `blocked` | 不自动发送，转人工处理 |
| `unknown` | 保守等待或转人工 |
| agent 不存在 | 启动/恢复或报错 |

虽然业务需求说“等待 idle”，实现上建议把 `done` 也视为可接收状态，避免 Herdr 的完成提醒状态造成无意义阻塞。

消息状态机：

```text
CREATED
  ↓ 路由校验
ROUTED
  ↓ 目标 idle/done
DISPATCHING
  ↓ Herdr 接受 prompt
DELIVERED
  ↓ 可选：等待目标 agent 完成
COMPLETED
```

异常状态：

```text
ROUTED → WAITING_TARGET
WAITING_TARGET → TIMEOUT
WAITING_TARGET → TARGET_BLOCKED
DISPATCHING → RETRYING
RETRYING → FAILED
```

轮询版伪代码：

```python
async def dispatch(message):
    route.validate(message)
    target = registry.resolve(message.target_agent_id)
    deadline = monotonic() + message.timeout_s
    delay = 0.5

    while monotonic() < deadline:
        state = herdr.get_agent(target.pane_id)

        if state.status in {"idle", "done"}:
            result = herdr.send_prompt(
                target.pane_id,
                render_message(message),
            )
            if result.accepted:
                journal.mark_delivered(message.id, target)
                return result

        elif state.status == "blocked":
            journal.mark_blocked(message.id, state)
            return DispatchResult.blocked(state)

        await sleep(delay)
        delay = min(delay * 1.5, 5.0)

    journal.mark_timeout(message.id, target)
    return DispatchResult.timeout()
```

推荐分两阶段：

- 第一阶段：0.5 秒开始轮询，逐步退避到 1、2、5 秒，单条消息设置总超时。
- 第二阶段：使用 Herdr Socket API 的事件订阅和状态等待，轮询只作为断线重连后的兜底。

## 9. Agent 自己发起通信

验证 agent 完成 UART UVM 验证后，可以调用项目级命令：

```bash
soc-agent-msg send \
  --source soc-a/uart/verification \
  --target-role software \
  --event verification.completed \
  --ip uart \
  --artifact /workspace/soc-a/uart/verification/report.md \
  --message "uart 已完成 UVM 验证，请开始驱动程序和 HAL 库开发"
```

该命令内部完成：

```text
source identity
→ 根据 project_id + ip_id + target_role 查 registry
→ 路由图校验
→ 等待目标 idle/done
→ 调用 Herdr agent prompt
→ 写入 message journal
```

不建议让每个 agent 自己拼接 pane ID。agent 只需要知道自己的业务身份和目标角色，路由层负责解析当前 pane。

消息建议携带结构化字段：

```json
{
  "id": "evt-uuid",
  "project_id": "soc-a",
  "ip_id": "uart",
  "source": "soc-a/uart/verification",
  "target": "soc-a/uart/software",
  "event_type": "verification.completed",
  "message": "uart 已完成 UVM 验证",
  "artifacts": ["/workspace/soc-a/uart/verification/report.md"],
  "correlation_id": "uart-flow-001"
}
```

## 10. 动态生命周期

创建一个 IP agent：

```text
1. 找到对应 role 的 tab
2. 创建或复用该 tab 下的 shell pane
3. 设置 pane 显示名，例如 verification-uart
4. 注入 project、IP、role、agent_id 环境变量
5. 启动 fnx_dv/fnx_sw 或对应 Pi agent
6. 等待 Herdr 识别并登记 pane_id
7. 写入 registry
```

删除时区分：

- 停止 agent 进程但保留 pane。
- 关闭 pane，但保留业务注册信息以便恢复。
- 从项目拓扑和 registry 中彻底删除。

默认建议先采用“停止进程、保留注册信息和事件历史”的可恢复策略。

允许重命名 workspace、tab、pane 的显示名称，但不允许因此改变 `project_id`、`ip_id`、`role`、`agent_id`。

## 13. 当前设计结论

你的需求适合采用三层结构：

```text
Pi 二次开发 Agent
        ↓ 稳定业务命令
Python Agent Orchestrator
        ↓ 路由、状态、队列、registry、审计
Herdr CLI / Socket API
        ↓ 终端布局和 agent 运行时
Workspace / Tab / Pane / Process
```

- Herdr 解决“在哪里运行、如何创建、如何寻址、如何读取状态和发送输入”。
- Python 编排层解决“谁能和谁通信、消息什么时候发送、如何等待、如何重试和如何审计”。
- Pi 二次开发 agent 解决 Spec、RTL、UVM、驱动、HAL 等专业任务。
